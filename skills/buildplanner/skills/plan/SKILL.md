# 개발 계획서 작성

아이디어 하나를 받아 **실제로 착수 가능한 개발 계획서**로 만든다.
결과물은 프로젝트의 `docs/BUILD-PLAN.md` 파일이다.

대상 아이디어: $ARGUMENTS

## 진행 상황 보고 (필수)

각 단계에 **들어갈 때마다** 워크스페이스 루트의 `.buildstudio/status.json`을 덮어쓴다.
BUILD STUDIO 시작 화면이 이 파일을 읽어 진행 상황을 표시한다. 폴더가 없으면 만든다.

```json
{ "kind": "plan", "step": 2, "label": "조사 중 — GitHub, 모델, 논문, 커뮤니티", "done": false }
```

`step`은 아래 단계 번호(1~4). 마지막에 계획서를 다 쓰면 `"step": 4, "done": true`와
`"file": "docs/BUILD-PLAN.md"`를 넣어 한 번 더 쓴다. 이 파일은 사용자에게 보여줄 내용이
아니므로 터미널에 언급하지 않는다.

## 원칙

- **계획서는 사용자가 대화하는 언어로 쓴다.** 한국어로 말하면 한국어로, 영어로 말하면 영어로.
  단 코드·식별자·경로·명령어·라이브러리 이름·URL은 원문 그대로 둔다.
- **조사 없이 쓰지 않는다.** 아래 2단계를 건너뛰고 일반론으로 계획서를 채우면 안 된다.
  실제로 존재하는 저장소·모델·논문을 링크와 함께 인용한다.
- **모르는 건 모른다고 쓴다.** 찾지 못한 항목은 그럴듯하게 지어내지 말고 "해당 없음"으로 남긴다.
- 사용자는 프로그래머가 아닐 수 있다. 전문 용어를 쓸 때는 한 줄로 풀어준다.

## 1단계 — 아이디어 파악

`$ARGUMENTS`가 비어 있으면 무엇을 만들고 싶은지 먼저 묻는다.

입력 끝에 `— 형태: 웹앱, 사용자: 나만, 출발점: 새로 시작` 같은 꼬리표가 붙어 있으면
**이미 받은 답이다. 다시 묻지 않는다.** BUILD STUDIO 시작 화면에서 사용자가 고른 값이다.

거기에 없는 것 중 계획을 갈라놓을 만한 지점만 묻는다. 사소한 선택은 묻지 말고
합리적인 기본값으로 정한 뒤 계획서에 "가정"으로 명시한다.

**되묻기는 최후의 수단이다.** 질문은 터미널에 뜨는데 사용자는 보통 다른 화면을 보고
있어서, 한 번 물으면 작업이 그대로 멈춘다. 물어야만 답이 갈리는 경우가 아니면 묻지 않는다.

현재 폴더에 이미 코드가 있으면 훑어본다. `Glob`으로 구조를 보고 `package.json`,
`requirements.txt`, `README.md`, `CLAUDE.md` 같은 파일을 읽는다.
기존 코드가 있으면 계획서는 **처음부터가 아니라 그 위에 얹는 형태**로 써야 한다.

## 2단계 — 조사

`WebSearch`로 네 갈래를 찾는다. 검색어는 **영문 기술 키워드**로 만든다
(한국어로 검색하면 결과가 빈약하다). 예: "실시간 음성 번역 앱" → `realtime speech translation`

| 갈래 | 찾을 것 |
|---|---|
| GitHub | 바로 갖다 쓸 수 있는 오픈소스. 스타 수, 최근 커밋, 라이선스 |
| Hugging Face | 필요한 모델이 이미 있는지 |
| 논문 / Papers with Code | 핵심 기법과 한계 |
| Hacker News / 커뮤니티 | 실제로 써본 사람들이 어디서 막혔는지 |

유망한 후보는 `WebFetch`로 실제 페이지를 열어 확인한다. **검색 결과 요약만 믿지 않는다.**
라이선스는 특히 직접 확인한다 — GPL인지 MIT인지가 계획을 바꾼다.

## 3단계 — 판단

조사 결과를 근거로 정한다.

- **핵심 기술** — 이 제품을 성립시키는 기술 (최대 8개)
- **구현 난이도** — 🟢 초급 / 🟡 중급 / 🟠 고급 / 🔴 전문가. **왜 그 난이도인지 한 문장**을 반드시 붙인다
- **기술 스택** — 프론트엔드 / 백엔드 / AI·ML / 데이터베이스 / 배포. 각 선택의 이유를 한 줄씩
- **핵심 기능** — 최대 8개. MVP에 들어갈 것과 나중 것을 구분
- **개발 단계** — 단계별 기간과 작업. 1단계는 반드시 **1~2주 안에 눈에 보이는 결과가 나오는** 크기로
- **리스크** — 각 리스크마다 대응 방안을 짝지어 쓴다. 대응 없는 리스크는 적지 않는다
- **라이선스 주의사항** — 인용한 오픈소스 중 상업적 이용에 제약이 있는 것

## 4단계 — 계획서 작성

`docs/BUILD-PLAN.md`에 아래 구조로 쓴다. 폴더가 없으면 만든다.
이미 파일이 있으면 덮어쓰기 전에 사용자에게 알린다.

```markdown
# 앱 개발 계획서: <제품명>

> 생성일: <오늘 날짜>
> <한 줄 요약>

---

## 1. 아이디어 개요
<3~5문장. 무엇을, 누구를 위해, 왜 지금>

### 구현 난이도
<이모지> **<난이도>** — <이유 한 문장>

## 2. 조사 키워드
- 주요 키워드: `<영문 검색어>`
- 수집 소스: GitHub (n), Hugging Face (n), 논문 (n), 커뮤니티 (n)

## 3. 참고 오픈소스
### [이름](URL)
<무엇이고, 이 프로젝트에 어떻게 쓰이는지>
- ⭐ 스타 · 언어 · 라이선스

## 4. 참고 AI 모델
## 5. 관련 논문/기술
## 6. 핵심 기능
## 7. 기술 스택
| 영역 | 기술 | 이유 |
## 8. 화면 구성
## 9. 개발 단계
| 단계 | 기간 | 작업 |
## 10. 리스크와 라이선스
| 리스크 | 대응 방안 |
## 11. 커뮤니티 반응
## 12. 유사 서비스
<있으면 쓰고, 이 제품이 무엇으로 다른지 한 줄>
```

해당 없는 섹션은 지우지 말고 `_해당하는 내용을 찾지 못했습니다._`로 남긴다.
나중에 다시 조사할 때 빈칸이 보여야 한다.

## 문서 레이아웃 규칙

읽는 사람이 훑어서 파악할 수 있어야 한다. 문단만 길게 늘어놓지 않는다.

- **리스크와 대응은 반드시 두 칸짜리 표로.** 대응 없는 리스크는 적지 않는다.
- **기술 스택도 표로** — 영역 / 기술 / 고른 이유 세 칸.
- **개발 단계도 표로** — 단계 / 기간 / 작업.
- **각 섹션은 한 줄 인용부호로 시작**해 무엇을 읽게 되는지 알린다.
- 기능·기술은 **굵은 제목 + 한 줄 설명** 형태의 목록으로. 통문단 금지.
- 한 문단은 세 문장을 넘기지 않는다.

## 5단계 — 마무리

계획서를 다 쓰면 사용자에게 **터미널에 짧게** 알린다. 계획서 전체를 다시 출력하지 않는다.

- 파일 경로
- 난이도와 그 이유
- **가장 먼저 할 일 한 가지** — 구체적인 첫 작업 하나
- 조사하면서 걸린 부분이 있으면 그것 (예: 핵심 라이브러리가 GPL이더라)

이어서 바로 개발을 시작할지 물어본다.
