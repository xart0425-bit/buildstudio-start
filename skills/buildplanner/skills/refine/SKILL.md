# 다듬은 것을 계획서에 되먹인다

계획서의 단계를 다 끝낸 뒤에도 고칠 일은 계속 나온다. 써 봐야 아는 느림, 눈에 띄는
떨림, 뒤늦게 생긴 요구. **그 결과가 계획서로 돌아가지 않으면 계획서는 "처음에 이렇게
만들려 했다" 에 멈추고, 실제 물건과 멀어진다.**

이 지시서는 그 되먹임을 한다. `docs/CHANGES.md` 의 **반영 대기** 항목을 읽고, 실제
코드와 대조해서, 문서 셋을 각자의 역할대로 고친다.

## 무엇을 어디에 적는가 (가장 중요)

세 문서에 **다른 것**을 적는다. 이 구분이 무너지면 계획서가 일지가 되고, 다른
프로젝트에서 꺼내 쓸 수 없는 문서가 된다.

| 문서 | 적는 것 | 적지 않는 것 |
|:--|:--|:--|
| `docs/BUILD-PLAN.md` | **지금 물건이 만족해야 하는 사양** | 언제 무엇을 고쳤는지 |
| `docs/BUILD-LOG.md` | 경위 · 무엇을 왜 그렇게 했는지 · **실패한 시도** | 사양 |
| `docs/PROGRESS.json` | 한 일 · 못 한 일 | 설명 |

예를 들어 "타임라인 그리기가 10.2ms 라 느렸는데 눈금을 캐시해서 0.27ms 가 됐다" 는
이렇게 갈라 적는다.

- 계획서 → `타임라인 한 번 그리기 0.3ms 이내`
- 일지 → `전체 선택자가 매 프레임 재계산을 부르고 있었다. 눈금을 캐시해서 10.2ms → 0.27ms.`
- 현황 → `{ "label": "타임라인 그리기 10.2ms → 0.27ms", "done": true, "tag": "성능" }`

계획서에 "10.2ms 였는데 0.27ms 로 고쳤다" 라고 적으면 그건 일지다. **계획서는 다음
사람이 이 물건을 다시 만들 때 읽는 설계도여야 한다.**

## 1단계 — 무엇을 반영할지 읽는다

`docs/CHANGES.md` 를 읽는다. 없으면 거기서 멈추고, BUILD STUDIO 개발 현황 화면의
`대화에서 모으기` 를 먼저 누르라고 알린다.

**`## 반영 대기` 절의 항목만** 대상이다. `## 보류` 와 `## 반영함` 은 건드리지 않는다 —
사람이 일부러 빼 둔 것이다.

## 2단계 — 실제 코드와 대조한다 (필수)

반영 대기 항목은 **요청**이지 결과가 아니다. 시켰다고 다 된 것도 아니고, 시킨 것보다
더 된 것도 있다. **짐작하지 않는다.**

항목마다 코드를 열어 확인한다.

- 실제로 들어갔는가 → 어디에 어떻게 들어갔는지 파일을 짚는다
- 안 들어갔거나 하다 말았는가 → 그대로 둔다. **지우지 않는다**
- 수치로 말할 수 있는가 → **수치로 적는다.** `빨라졌다` 가 아니라 `2132ms → 171ms`.
  느낌으로 적으면 다음에 또 느려졌을 때 견줄 기준이 없다

확인이 안 되는 항목은 사용자에게 묻는다. 물어볼 것이 여러 개면 한 번에 모아 묻는다.

## 3단계 — 개발 계획서를 고친다

`docs/BUILD-PLAN.md` 를 **지금 물건에 맞게** 고친다. 덧붙이기만 하지 않는다 — 어긋난
곳은 고쳐 쓴다.

- 기능이 늘었으면 **핵심 기능** 절에 사양으로 적는다
- 화면이 바뀌었으면 **화면 구성** 절을 지금 화면으로 고친다
- 성능·품질 기준이 생겼으면 그 절에 수치로 적는다. 절이 없으면 만든다
- 스택이나 방식을 바꿨으면 **기술 스택** 절을 고치고, 왜 바꿨는지는 일지에 적는다

계획서의 개발 단계는 손대지 않는다. 이미 지나온 계획이고, 지금 상태는 현황이 안다.

## 4단계 — 개발 현황에 남긴다

`docs/PROGRESS.json` 의 **마지막 단계**에 항목을 덧붙인다. 마지막 단계가 이미 다
끝났으면 새 단계를 만든다.

```json
{
  "no": 6,
  "name": "다듬기와 보강",
  "note": "계획 단계를 끝낸 뒤에 나온 일들이다 — 미리 정해 둔 게 아니라 쓰면서 생긴다.",
  "tasks": [
    { "id": "6-1", "label": "비교 탭 첫 열기 2132ms → 171ms", "done": true, "tag": "성능" },
    { "id": "6-2", "label": "창 크기 조절이 느림 (145ms) — 해결책 미정", "done": false, "tag": "성능" }
  ]
}
```

- **못 고친 것도 `done: false` 로 남긴다.** 지우면 없던 일이 된다
- `tag` 는 그 파일에 이미 쓰이는 값을 먼저 쓴다. 새로 만들 때는 한 낱말로
- `asOf` 를 오늘 날짜로 고친다

## 5단계 — 개발 일지에 경위를 적는다

`docs/BUILD-LOG.md` 맨 위에 덧붙인다.

```markdown
## <날짜> — 다듬기 반영

**고친 것**
- <무엇이 어떻게 됐는지. 수치가 있으면 수치로>

**실패한 시도**
- <해 봤는데 안 됐던 길과 그 이유>

**남은 것**
- <못 고친 것. 없으면 "없음">
```

**실패한 시도를 빼지 않는다.** 안 되는 길을 다음 사람이 또 걷지 않게 하는 유일한
방법이다. 여기를 비우면 같은 벽에 두 번 부딪힌다.

## 6단계 — 변경 기록을 정리한다

반영한 항목을 `docs/CHANGES.md` 의 `## 반영함` 절로 옮기고 `- [x]` 로 표시한다.
시각 표시(`` `09-06 21:12` ``)는 그대로 둔다.

확인하지 못했거나 사용자가 미룬 항목은 `## 보류` 로 옮긴다. **반영 대기에 남겨 두거나
지우지 않는다** — 남겨 두면 다음에 또 올라오고, 지우면 없던 일이 된다.

## 진행 상황 보고 (필수)

시작할 때와 끝낼 때 워크스페이스 루트의 `.buildstudio/status.json` 을 덮어쓴다.

```json
{ "kind": "refine", "step": 1, "label": "변경 기록을 읽는 중", "done": false }
```

끝나면 `{ "kind": "refine", "step": 6, "label": "반영 완료", "done": true, "file": "docs/BUILD-PLAN.md" }`.

## 규칙

- **반영 대기 항목만 건드린다.** 보류와 반영함은 사람의 판단이다
- **짐작해서 적지 않는다.** 코드에서 확인한 것만 적는다
- **수치로 말할 수 있는 것은 수치로 적는다**
- **못 한 것을 지우지 않는다.** `done: false` 로 남긴다
- 계획서에는 사양을, 일지에는 경위를. 섞지 않는다
- 사용자가 대화하는 언어로 쓴다. 코드·명령·식별자는 원문 그대로

## 마무리

터미널에 짧게 보고한다 — 계획서의 어느 절이 바뀌었는지, 현황에 몇 개가 들어갔는지,
그리고 **보류로 넘긴 것이 있으면 무엇을 왜** 넘겼는지.
