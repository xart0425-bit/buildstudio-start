# 기능 소개 문서 만들기

`README.md` 를 만든다. 이건 **저장소에 온 사람이 가장 먼저, 대개 유일하게 읽는 문서**다.

## 진행 상황 보고 (필수)

각 단계에서 워크스페이스 루트의 `.buildstudio/status.json` 을 덮어쓴다.

```json
{ "kind": "readme", "step": 2, "label": "기능 정리", "done": false }
```

다 쓰면 `"step": 3, "done": true, "file": "README.md"` 로 한 번 더 쓴다.

## 1단계 — 코드를 읽고 파악한다

**추측해서 쓰지 않는다.** 실제로 있는 것만 쓴다.

- `package.json` — 이름, 설명, 스크립트, 의존성
- 진입점과 주요 소스 — 이 앱이 실제로 무엇을 하는가
- `docs/` — 계획서나 역설계 문서가 있으면 의도를 알 수 있다
- 스크린샷·아이콘이 있으면 경로를 기억해 둔다

없는 기능을 그럴듯하게 지어내면, 읽는 사람이 속고 나서 신뢰를 잃는다.

## 2단계 — 구조

```markdown
# <이름>

<한 줄. 무엇을 하는 물건인지. 형용사 말고 동작으로.>

<스크린샷이 있으면 여기>

## 무엇을 할 수 있나

- **<기능>** — <한 줄 설명>

## 시작하기

```bash
<실제로 되는 명령. package.json 의 scripts 에서 가져온다>
```

## 어떻게 만들어졌나

<주요 기술과 그것을 고른 이유. 나열만 하지 않는다>

## 알아둘 것

<제약, 미구현, 주의사항>
```

## 규칙

- **첫 줄이 전부다.** 스크롤하지 않고 읽는 사람이 대부분이다. "무엇을 하는 물건인가"를 한 문장으로.
- **명령은 실제로 되는 것만.** `package.json` 에 없는 스크립트를 적지 않는다.
- 배지·이모지 남발하지 않는다. 하나도 없어도 좋은 문서가 된다.
- 한 문단은 세 문장을 넘기지 않는다.
- 설치·실행이 특정 환경을 요구하면(OS, 런타임 버전, 계정) **반드시 적는다.**
- **못 하는 것도 적는다.** "알아둘 것"이 비어 있는 문서는 대개 정직하지 않은 문서다.
- 사용자가 대화하는 언어로 쓴다. 코드·명령·식별자는 원문 그대로.

## 3단계 — 마무리

이미 `README.md` 가 있으면 **덮어쓰기 전에 무엇이 바뀌는지 알린다.**

터미널에는 짧게 보고한다 — 파일 경로, 문서에 담은 기능 수, 그리고
**코드를 읽다가 발견했지만 문서에 못 쓴 것**(미완성 기능, 깨진 링크 등)이 있으면 그것.
