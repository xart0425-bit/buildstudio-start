# 역설계 — 원리를 뽑아 더 나은 것을 설계한다

대상: $ARGUMENTS

이건 **복제가 아니라 재설계**다. 원본을 더 잘 만드는 게 아니라,
원본이 피할 수 없었던 제약을 걷어내서 이긴다.

## 진행 상황 보고 (필수)

각 단계에 **들어갈 때마다** 워크스페이스 루트의 `.buildstudio/status.json`을 덮어쓴다.
BUILD STUDIO 시작 화면이 이 파일을 읽어 진행 상황을 표시한다. 폴더가 없으면 만든다.

```json
{ "kind": "teardown", "step": 3, "label": "균열 찾기 — 원본이 감수한 타협", "done": false }
```

`step`은 아래 단계 번호(1~6). 문서를 다 쓰면 `"step": 6, "done": true`와
`"file": "docs/TEARDOWN.md"`를 넣어 한 번 더 쓴다. 이 파일은 사용자에게 보여줄 내용이
아니므로 터미널에 언급하지 않는다.

## 지켜야 할 선

- **공개된 정보만 본다.** 공식 페이지, 문서, 커뮤니티 반응, 오픈소스.
- **소스코드와 UI 에셋은 베끼지 않는다.** 뽑아내는 건 오직 **작동 원리**다.
- 결과물에 원본의 문구·이미지·코드를 옮겨 담지 않는다.
- 계획서는 사용자가 대화하는 언어로 쓴다. 코드·식별자·제품명은 원문 유지.

## 1단계 — 대상 파악

`$ARGUMENTS`가 비어 있으면 어떤 제품을 분석할지 묻는다.

입력 끝에 `— 목적: ..., 범위: ...` 같은 꼬리표가 붙어 있으면 **이미 받은 답이다.
다시 묻지 않는다.** BUILD STUDIO 시작 화면에서 사용자가 고른 값이다.

**되묻기는 최후의 수단이다.** 질문은 터미널에 뜨는데 사용자는 보통 다른 화면을 보고
있어서, 한 번 물으면 작업이 그대로 멈춘다.

제품명만으로 검색하면 홍보 기사만 나온다. **기술 도메인 키워드를 따로 만들어** 병행 검색한다.
(예: Notion → `block based editor`, `crdt collaborative document`)

공식 URL이 주어지면 `WebFetch`로 실제 페이지를 읽는다. 없으면 먼저 찾는다.

## 2단계 — 작동 원리 추출

**기능 목록이 아니다.** 이 제품을 성립시키는 *메커니즘*을 분해한다.

각 원리는 이렇게 쓴다.
- **무엇을** 하는가 (메커니즘)
- **왜** 그렇게 했는가 (그 선택이 푸는 문제)
- 그것이 **가능하게 만든 것**

3~7개면 충분하다. 찾지 못하면 "공식 URL이 정확한지 확인해달라"고 말한다.

## 3단계 — 균열 찾기

**여기서 도약이 시작된다.** 각 원리마다 원본이 *감수한 타협*을 찾는다.

- 이 설계가 포기한 것은 무엇인가
- 그 제약은 **당시의 한계**였나, **본질적인 한계**였나
- 지금은 사라진 제약인가 (새 모델·새 하드웨어·새 표준 때문에)

당시엔 불가피했지만 **지금은 아닌 것**이 가장 값진 균열이다.
커뮤니티에서 사람들이 반복해서 불평하는 지점도 같이 찾는다.

## 4단계 — 도약 설계

균열 위에 새 제품을 세운다.

- **컨셉명** — 새 제품의 이름
- **포지셔닝** — 한 문장
- **논지(thesis)** — 왜 지금 이게 가능한가, 왜 원본은 못 했는가
- **핵심 기능** — 균열에서 직접 도출된 것만. 원본 기능 나열 금지
- **구조적 전환** — 원본과 아키텍처가 어디서 갈라지는가
- **방어 요소** — 원본이 따라오려면 무엇을 버려야 하는가

## 5단계 — 차별화 감사 (자기 검증)

방금 만든 설계를 **스스로 공격한다.**

0~100점으로 채점한다. 점수는 "원본과 얼마나 다른가"다.
- 겹치는 지점을 구체적으로 나열하고, 각각에 대응 방안을 붙인다
- 법적으로 주의할 점 (특허, 상표, 라이선스)

**60점 미만이면 4단계로 돌아가 한 번 다시 설계한다.**
재설계는 딱 한 번만. 두 번 실패하면 균열이 얕았다는 뜻이니, 그 사실을 그대로 보고한다.

## 6단계 — 문서 작성

`docs/TEARDOWN.md`에 쓴다. 폴더가 없으면 만든다.

## 문서 레이아웃 규칙

읽는 사람이 훑어서 파악할 수 있어야 한다. 문단만 길게 늘어놓지 않는다.

- **문제와 대응은 반드시 두 칸짜리 표로.** 왼쪽에 문제/균열/리스크, 오른쪽에 대응/해결.
  이 짝이 문서에서 가장 중요한 정보다.
- **각 섹션은 한 줄 인용부호로 시작**해 무엇을 읽게 되는지 알린다.
- 원리·기능·장점은 **굵은 제목 + 한 줄 설명** 형태의 목록으로. 통문단 금지.
- 숫자로 말할 수 있는 건 표로. (점수, 개수, 기간)
- 한 문단은 세 문장을 넘기지 않는다.

## 7단계 — 마무리

터미널에는 **짧게만** 보고한다. 문서 전체를 다시 출력하지 않는다.

- 파일 경로
- 차별화 점수와 판정
- **가장 큰 균열 하나** — 이게 이 설계의 핵심이다
- 법적으로 주의할 점이 있으면 그것

이어서 계획을 실행에 옮길지 물어본다.
