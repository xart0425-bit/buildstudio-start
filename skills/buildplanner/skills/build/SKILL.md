# 계획서를 따라 만들기

`docs/BUILD-PLAN.md` 를 읽고, 거기 적힌 **다음 단계 하나**를 실제로 만든다.

한 번에 전부 만들지 않는다. 계획서는 단계로 나뉘어 있고, 그 단위가 사람이 확인할 수 있는 크기다.

## 진행 상황 보고 (필수)

각 단계에서 워크스페이스 루트의 `.buildstudio/status.json` 을 덮어쓴다.

```json
{ "kind": "build", "step": 2, "label": "뼈대 만들기", "done": false }
```

끝나면 `"step": 5, "done": true, "file": "docs/BUILD-LOG.md"` 로 한 번 더 쓴다.

## 1단계 — 계획서를 읽는다

`docs/BUILD-PLAN.md` 가 없으면 **거기서 멈춘다.** 계획 없이 짐작으로 만들지 않는다.
없다고 알리고, 먼저 계획을 세우자고 말한다.

읽을 것:

- 기술 스택 — 무엇으로 만들기로 했는가
- 개발 단계 — 어디까지가 1단계인가
- 이미 만들어진 것 — `docs/BUILD-LOG.md` 가 있으면 어디까지 왔는지 적혀 있다

## 2단계 — 개발 현황 문서를 세운다 (필수)

만들기 전에 `docs/PROGRESS.json` 이 있는지 본다. **없으면 여기서 만든다.** 건너뛰지 않는다 —
이 파일이 BUILD STUDIO 의 개발 현황 화면이 읽는 유일한 곳이고, 없으면 화면은 계속 비어 있다.

계획서의 개발 단계를 그대로 옮기고, 각 항목이 코드에 실제로 있는지 확인해서 `done` 을 정한다.
**짐작해서 true 로 적지 않는다.** 파일을 열어 확인한 것만 true 다.

```json
{
  "title": "<제품 이름>",
  "asOf": "<YYYY-MM-DD>",
  "stages": [
    {
      "no": 1,
      "name": "<계획서의 단계 이름>",
      "note": "<한 줄 설명>",
      "tasks": [{ "id": "1-1", "label": "<할 일>", "done": false, "tag": "<선택>" }]
    }
  ]
}
```

이미 있으면 새로 쓰지 않고, 코드와 대조해서 어긋난 `done` 만 고친다. 사람이 손으로 적어 둔
항목을 지우지 않는다.

## 3단계 — 어디부터 할지 정하고 알린다

**만들기 전에 무엇을 만들지 한 문단으로 말한다.** 파일 몇 개를 어떤 이유로 만드는지.
사용자가 "그건 아닌데"라고 말할 틈을 준다.

이미 있는 코드를 갈아엎어야 한다면 **반드시 먼저 묻는다.**

## 4단계 — 만든다

- 계획서에 적힌 스택을 쓴다. 더 낫다고 생각되는 게 있으면 **바꾸기 전에 말한다.**
- 실행되는 것을 만든다. 껍데기만 만들고 "완성"이라고 하지 않는다.
- 의존성을 넣으면 실제로 설치하고, 실행해서 뜨는지 확인한다.
- 확인하지 않은 것은 확인했다고 쓰지 않는다.

## 5단계 — 기록을 남긴다

`docs/BUILD-LOG.md` 에 덧붙인다.

```markdown
## <날짜> — <단계 이름>

**만든 것**
- `경로` — 무엇을 하는 파일인지

**확인한 것**
- <실제로 돌려본 것과 그 결과>

**남은 것 · 걸린 것**
- <다음 사람이 알아야 할 것. 없으면 "없음">
```

## 규칙

- **한 단계씩.** 계획서의 다음 단계 하나를 끝내고 멈춘다.
- **끝낸 것은 `docs/PROGRESS.json` 에 표시한다.** 만든 항목의 `done` 을 true 로 바꾸고
  `asOf` 를 오늘 날짜로 고친다. 이걸 빼면 일은 진행됐는데 현황 화면만 옛날 그대로 남는다.
- **돌려보고 말한다.** "될 것입니다"가 아니라 "돌려보니 이렇게 나옵니다".
- 실패하면 실패했다고 쓴다. 출력을 그대로 보여준다.
- 계획서와 다르게 만들었으면 **어디를 왜 다르게 했는지** 적는다.
- 사용자가 대화하는 언어로 쓴다. 코드·명령·식별자는 원문 그대로.

## 마무리

터미널에는 짧게 보고한다 — 만든 파일, 돌려본 결과, 그리고 **다음 단계가 무엇인지**.
